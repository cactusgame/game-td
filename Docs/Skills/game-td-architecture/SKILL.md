# game-td 项目开发规范

目标：在不重复依赖历史聊天的情况下，延续这个塔防建设游戏的领域语义、单一状态归属和可理解的实现。
默认项目是 `D:/projects/game-td`；其他路径的同一仓库也适用。不要因仅出现 Unity、DDD 或 ECS 就把规范套用到其他项目。

## 执行方式

1. 先确认当前仓库、相关 `AGENTS.md`、现有实现和用户本次目标。用户后续明确变更的需求优先；不要用历史原型限制阻止授权的改动。
2. 编码前明确：改变哪个业务模块、谁拥有可变状态、谁组织用例、哪个模拟边界生效、影响哪些查询/表现。
3. 新玩法先查看 [领域与依赖](references/architecture.md)。修改战斗、Job、碰撞、恢复或性能时查看 [ECS 规范](references/ecs.md)。
4. 修改地图、编辑器、配置或素材时查看 [地图与内容](references/map-content.md)。接手项目或需要判断历史约定时查看 [项目语义与阅读入口](references/project-context.md)。只加载本次相关参考。
5. 用当前代码和包文档验证 API，不从本技能猜测版本。可用时使用相应 Unity 专项技能进行 Editor、包、Sprite、Atlas 操作；本技能不替代其工具用法。

## 长期架构约定

- DDD 划分业务职责，整洁架构约束依赖，ECS 实现高频模拟，Unity 适配输入/内容/表现，VContainer 组装托管服务。
- 领域边界不等于每个游戏名词或每个程序集。英雄、怪物、塔共用稳定战斗能力；不要给每种对象复制完整生命周期或建立巨型基类。
- 每个可变状态只有一个权威拥有者。采用 ECS 的生命、位置、冷却和效果不再同步保存到另一套托管 Unit/Building 对象中。
- `Domain` 放业务模型、值对象与纯规则；`Application` 放用例和一致性协调；`Contracts` 放公开命令/结果/快照/端口；`Simulation` 放 ECS 运行实现；`Unity`/`Presentation` 放引擎适配和视图。
- 纯 Domain/Application/Contracts 不依赖 UnityEngine、Entities、DI 容器或文件系统；对确有收益的数值库依赖需明确决定。ECS 层可以依赖 Burst 兼容的 Domain 规则。
- 跨模块不取得并任意修改内部聚合或 ECS 组件。低频业务走公开应用契约；高频战斗走统一数据组件和有明确写入职责的系统。
- 跨模块双向业务由小型协调器连接，程序集依赖单向。消费者端口由消费者拥有，提供者公共能力放其 Contracts，二者按需求选择。
- 命令要有执行结果；查询只读；事件只表达已提交事实。排队成功不等于操作已完成，核心一致性不能依赖全局订阅顺序。
- 建造/扣费、升级/属性更新、拆除/退款、破坏/通行、日结标记/入账需要明确的完整提交或回滚语义。表现失败可从状态重建。
- 稳定领域 ID 与 Unity InstanceID、ECS Entity 区分。世界版本、导航版本、存档版本、内容版本各有含义。

## ECS 与生命周期底线

- 高频单位状态用数据组件；移动、寻敌、命中、伤害、效果用批量系统。领域不变量通过组件写入职责、验证与系统顺序维护，不要求每个 ECS 实体都有一个 C# 聚合对象。
- 普通账户、出战方案、编组、拓扑、玩家档案等可继续用对象模型；是否转 ECS 根据真实数据量与性能决定。
- VContainer 管应用服务、加载器、输入和 ECS 桥接器，不为每个怪物建作用域，不把托管服务注入 Burst 热路径。
- World 由明确会话拥有者创建/销毁，只保留一个模拟驱动；当前原型手动推进独立 World，不同时追加到默认 PlayerLoop。
- 并行写入、事件归并、结构变化和快照捕获都需要明确同步点。优先按实体局部更新；同一目标受多源写入时先收集再受控归并。
- 配置、运行状态、表现资源分开。玩家输入转换为意图，模拟输出快照，Sprite/动画/UI 读取结果；表现不能裁决伤害和死亡。
- 固定步与模拟时钟推进玩法；动画结束、真实时间延迟或 UI 回调不能成为唯一战斗时序。
- 恢复/重启要处理旧命令、旧异步结果、随机流、ID 映射和表现缓存；局外永久奖励不随局内快照倒退。

## 可读性要求

- 用户已反馈首版难读。默认采用明确命名、常规多行格式；关键业务流程不要压缩成一行、多重三元表达式或多个分号串联。
- 类与重要方法说明职责、调用者、状态归属；复杂 ECS Query、Job 依赖和提交顺序说明原因。不要给每行简单赋值加噪声注释。
- 一个类聚焦一个职责；新增独立入口类通常使用同名文件。不要仅为形式给所有类加接口、事件或通用框架。
- 交付时给出实际入口、从输入到状态再到画面的调用链，以及本次应先读的少量文件。
- 解释架构时优先使用项目中的真实用例，例如建塔、破墙、英雄接触怪物；区分规则归属和技术实现。

## 验证与交付

- 业务规则验证不变量；跨模块用例验证失败不留下半完成状态；ECS 验证系统顺序、接触去重/死亡/边界/随机重置等实际行为。
- UI/素材修改检查运行画面、输入和真实 Atlas 打包；重启/恢复检查状态、引用与生命周期。
- 性能改动区分 CPU 模拟、快照同步、渲染提交、GPU、GC 与内存；小规模 Editor FPS 不证明手机或万单位能力。
- 报告已执行的编译、测试、运行验证及其边界。不得把旧结果当成本次已验证，也不要为文档修改启动无关场景改动。
- 不自动把推荐框架全部安装，不因应用本技能自动重构全仓库。保留现有工作，按本次任务增量演进。
