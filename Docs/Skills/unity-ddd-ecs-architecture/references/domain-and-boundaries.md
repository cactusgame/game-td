# 领域模型、模块与依赖

## 统一术语与限界上下文

与玩家、策划和开发者使用同一套明确术语，例如对局、部署、建造、投资、冷却、命中、死亡、奖励。相同词在不同上下文含义不同时，记录转换关系：内容库中的“怪物”是定义，对局中的“怪物”是运行实例，图鉴中的“怪物”是已发现条目。

按规则、语言、生命周期和一致性划分边界。战斗、经济、任务、成长可成为候选模块，但一个小型游戏不需要立即拆成多个上下文或程序集。角色类别通常共享战斗能力，不因此各自成为完整上下文。

跨边界时明确提供方、消费方、公开契约和模型转换。外部存档、SDK、网络或遗留模型与本地语义不一致时使用反腐败转换；简单稳定数据不需要多层包装。REST、微服务和分布式消息不是单机游戏的默认方案。

## 对象模型与 ECS 的选择

| 场景 | 首选考虑 | 不变量的实现位置 |
| --- | --- | --- |
| 资源账户、任务进度、编队、装备方案 | 小型普通对象模型 | 聚合行为、值对象与纯规则 |
| 大量生命、位置、冷却、效果状态 | ECS 非托管组件与批量系统 | 写入系统、规则函数与执行边界 |
| 少量但规则复杂的战斗对象 | 普通对象或混合方案 | 根据真实需求选择 |
| 内容创作与配置 | Unity Authoring / 数据文件 | 加载/烘焙校验，生成运行定义 |
| UI、动画与音效 | Unity 表现适配 | 不拥有玩法真值 |

DDD 不等于面向对象类图，ECS 也不等于无领域模型。对 ECS 状态的业务约束应能用领域语言说明，并有规则、写入职责与测试证明。

## 实体、值对象、聚合与服务

- 实体具有在其领域范围内稳定的身份；不要依靠内存地址、InstanceID 或跨 World 的 Entity 值。
- 值对象按值比较、创建时验证、对外不可变。ECS 的可变数值组件不会因此自动成为 DDD 值对象。
- 聚合是需要立即维护的不变量边界，通常保持小型，跨聚合使用 ID 引用。不是所有引用关联都属于同一聚合。
- 对象聚合通过 `SpendResources`、`EquipItem`、`CompleteQuest` 等行为改状态，避免公共 setter 或暴露内部可变集合。
- 无法自然归属单个实体/值对象的业务规则可以放领域服务或纯规则函数；不要为了“所有不变量都在聚合”把多对象规则强塞入某个类。
- 应用服务协调授权、校验、领域行为、外部端口和提交边界，不替代领域规则。
- ECS 的一致性边界可能涉及多个实体和系统；不要求每个组件或每个 Entity 对应一个聚合根。

## 目录与程序集

目录职责与内部命名以 [代码规范](code-conventions.md) 及技能正文的“代码规范”为准。以下展示层间位置，不批量迁移已有目录：

```text
Game/
  Gameplay/
    Battle/
      Contracts/       命令、结果、快照、公开端口
      Domain/          稳定 ID、数值语义、纯规则、对象模型
      Application/     用例、协调与会话边界
      Simulation/      ECS 组件、系统、模拟实现
      Unity/           Authoring、引擎适配和视图
    Economy/
    Progression/
  SharedKernel/        已稳定且确实共享的最小语义
  Infrastructure/      存档、平台、网络等端口实现
  Bootstrap/           组装、会话和 World 生命周期
```

依赖约束：

```text
Domain -> 最小共享语义及已批准的纯数值依赖
Contracts -> 最小共享语义 / 必要的稳定领域类型
Application -> Domain + Contracts + 所需模块的公开契约
Simulation -> Burst 兼容的规则与类型 + Contracts + ECS 技术包
Unity / Presentation -> Application / Contracts / 必要的模拟表现适配
Infrastructure -> 消费者定义的端口
Bootstrap -> 具体实现的组装
```

Application 通过端口使用模拟实现，端口可归 Application 或稳定 Contracts；Simulation 实现端口。不得为了访问实现产生 Application 与 Simulation 的循环引用。Simulation 依赖 Entities，不因复用领域规则而把 Entities 依赖传入 Domain。

稳定边界可用 asmdef 固定，纯程序集可使用 `noEngineReferences`。文件夹不能替代编译依赖检查。Editor 代码不能被 Runtime 引用。

## 仓储、工厂与查询

对象聚合需要持久化或集合语义时使用 Repository，接口默认归 Domain；若项目将持久化视为应用用例能力，也可由 Application 拥有端口并记录理由。具体实现放 Infrastructure。实体不自行调用仓储。

不要为每个 ECS 组件创建 Repository，或为 UI 每帧逐实体读取聚合。模拟通过批量命令和只读快照提供能力；查询可使用专用读模型，不强迫重建聚合。

复杂对象创建由工厂确保初始有效；ECS 出生由受控创建阶段校验定义并初始化必要组件。运行配置与创作资产分离，恢复数据通过验证和版本迁移进入运行世界。

共享代码按稳定能力提取，例如阵营、伤害计算、空间语义。避免万能 UnitBase、全局可变 Context 或随意取服务的 Service Locator；DI 容器仅在组装层使用。
